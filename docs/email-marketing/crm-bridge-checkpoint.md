# Email CRM bridge checkpoint

Local continuation after `a51fc103`. This is a partial EM-014 implementation, not a production rollout or a completed email product.

## Connected behavior

1. An operator takes over the current conversation and reviews one exact inbound message. The callback form captures that message and content revision, preserves phone/time wording and has an unchecked seller-interest assertion. A new reply disables the old review until the operator explicitly reviews the latest reply; the API also rejects older message evidence even with a fresh revision. A phone-only reply can save a handoff without the interest assertion; it stays in CRM review and creates no Lead/task.
2. The server validates active memberships, current thread revision, evidence, sender identity and exactly one confirmed canonical property. Buyer, shared, conflicting, unresolved and multiple-property cases remain held with an explicit reason.
3. The bridge links an existing canonical person/property Lead when unambiguous. Existing active Lead/Opportunity stage and original source remain unchanged. A different or absent CRM owner, a New/unknown stage, or a parked/closed/dead record requires review. Email does not perform an implicit reassignment or lifecycle transition.
4. A new email-only Lead is inserted at `contacted`/`lead` with source `email_marketing` and the server-resolved owner. The canonical trigger must resolve to the reviewed person/property or the entire command rolls back. A reply phone remains evidence on the callback; it is not silently made the canonical primary phone.
5. Immutable Email messages project exactly once into `lead_activities`, with `activity_type=email`, direction, thread/message/campaign IDs, original timestamp, body and content hash. This is the input used by existing Conversations and recognized by the mobile email filter. A projection receipt and exact conflict checks prevent attaching a duplicate message to a different record. New inbound/human outbound messages keep this history current after the initial bridge.
6. `create_work_item_v2` creates one non-primary Acquisitions callback review task. Its key is derived from the handoff ID; the bridge verifies replayed task provenance. Requested time remains verbatim. The due date means “review this callback request by,” uses configured weekday hours and urgent SLA, and does not assert that a call is scheduled.
7. Lead/link/history/attribution/task/notification/audit/receipt commit in one PostgreSQL transaction. Missing canonical functions/identity guard save a held local handoff. An unexpected write failure rolls back the whole command and can be retried with the same command key.
8. Marketing stops and reduced membership access block open linked callback tasks through their durable activity source and add a work-item event. Completed/cancelled/blocked tasks remain in their current state. For updates after the initial bridge, history and callback holds use separate savepoints. A damaged CRM projection cannot undo a received opt-out, suppression or local send cancellation. Each failed update becomes a private durable repair job with an owner notification; the Inbox distinguishes an unapplied callback hold from a successfully blocked task.
9. `OPS-REPLAY` lets an owner retry the exact pending internal CRM job after reviewing its effect. It checks the current failure code, retains reason/audit/receipt and reuses message/task identities. Automatic retries also run on later relevant thread events. This creates no provider send, calendar event, dialer call, SMS, push or advertising conversion. It does not retry an initial held handoff.

## Concurrency and compatibility

`20260912181000_email_crm_identity_guard.sql` adds a private person/property claim for Email-created Leads and a BEFORE INSERT lock for every Lead insert that resolves that same known canonical pair. Email takes the identical lock before searching existing Leads. An earlier external insert finishes its canonical projection before Email searches; a later conflicting insert gets `EMAIL_CRM_IDENTITY_ALREADY_LINKED`. Same-ID upserts continue to PostgreSQL conflict handling. A parked/terminal claim permits later intake. This is a narrow intake safeguard, not universal identity deduplication or a merge engine. Unknown email/property matches and later identity edits require separate reconciliation.

`20260912180000_email_crm_bridge.sql` deliberately makes `leads.phone` nullable and adds `email_marketing` to the exact installed source CHECK expression. It preserves existing allowed source values and validation/inheritance state, and refuses ambiguous or multi-column source constraints. These are canonical compatibility changes requiring live-schema rehearsal before release. They have only been applied to disposable databases. The claim guard also needs release testing against existing intake/upsert clients so they handle a duplicate response usefully.

The earlier Email bootstrap incorrectly assumed `agent_profiles.user_id/name/is_active`. It now maps auth users to the current CRM `email/full_name` profile contract, stores separate IDs, and uses explicit Email membership activity plus profile existence. It does not claim a nonexistent CRM deactivation field. Supabase authentication remains the session authority.

## Verification boundary

The fixture loads the actual canonical entity foundation migration and copied, checked production work-item bodies. It supplies a reduced Conversations projection for the `lead:<id>`/email/needs-reply contract. Local browser tests use the shared component and command API with fabricated identities. They prove neither real CRM sign-in nor the full deployed Conversations/mobile workflow.

The implementation intentionally leaves these items open: held-handoff resolution and retry UI, accept/reassign/outcome commands, canonical owner changes after linking, true Lead revision/qualification integration, timed escalation, live provider transport, subscriptions, Google Calendar, response phone line and full CRM-shell verification. No deployed migration, production record, subscription or customer communication was created by this build.
